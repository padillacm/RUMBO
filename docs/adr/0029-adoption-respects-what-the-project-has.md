# ADR-0029: Adoption respects what the project already has, and never destroys what the human wrote
Status: proposed    Date: 2026-11-20

Completes ADR-0013 (adopting an existing project) and ADR-0020 (adoption follows the layout the
project has); narrows one sentence of ADR-0011 and one of ADR-0014. All four stand.

## Context
The second audit before v0.4.1 (`docs/audits/2026-11-16-pre-0.4.1.md`, section 6, C1 to C11)
mounted the harness on projects that were not written for it, and ran `init`, `update` and
`promote` twice. What it reproduced has one root: the commands decided for the project, or over
it, where the project had already decided.

1. **`--force` lost the human's text (C1).** The backup was always `<file>.bak`: the second run
   copied the template the first run had written over the only copy of the signed
   `docs/decisions.md`. `rumbo doctor` recommended `init --force` for a missing lock file.
2. **Adoption imposed a pytest configuration (C2).** `testpaths = ["tests"]` and
   `--strict-markers` were appended to `pyproject.toml`: tests that lived elsewhere stopped being
   collected (a green suite without the suite), and a configuration in `setup.cfg` or `tox.ini`
   was outranked.
3. **The Python version was never looked at (C3).** `requires-python = ">=3.13"` got a harness
   on 3.11, and a `.python-version` that uv then refuses.
4. **`promote` wrote the rigor before it knew it could finish (C4)**, and a hand-edited
   `[tool.rumbo]` ended `update` and `promote` in a traceback.
5. **`update` downgraded a newer harness without a word (C5).**
6. **An existing `.claude/settings.json` or `.pre-commit-config.yaml` was skipped, and with it
   the guard (C6)**; `doctor` said "complete". `pre-commit autoupdate` rewrote the revisions of
   a configuration RUMBO had not written.
7. **Adoption configured what was not there (C7):** a package directory that did not exist,
   import-linter layers and an evals entry for modules nobody wrote, a project without
   `[build-system]` whose package is not installed.
8. **`app`, `api` and `domain` were refused as package names for every project (C8).**
9. **RUMBO's own `ci.yml` and `infra/` counted as the project's on the next command (C9)**, so
   their drift and their deletion were never reported.
10. **Small ones (C10, C11):** `tests/architecture/` hard-coded in the drift report; the
    version key not found after an array; `isatty()` where `is_console` was meant; CRLF from
    `new`, `decision`, `eval add` and `tour --out` on Windows; a decision title that carried a
    second heading; a date read as a document number; an error half-way through `init` that
    left half a harness; "not a git repository" in a sub-directory of one.

## Drivers (non-functional requirements)
A project generated by `rumbo init` must not change by a byte. Nothing the human wrote is
overwritten without a copy, and no copy is overwritten. A fact about the project is decided
once and stored in `[tool.rumbo]`, never guessed again (ADR-0020). An adopted project's
`rumbo check` is green on day one, or the command says before writing why it cannot be.
Standard library only: no TOML writer, no `packaging`.

## Options considered
For what adoption does when the configuration names modules that are not on disk (C7):
1. **Generate the configuration without them** (no contracts, no `arch` and `evals` steps) and
   bring them back when the modules appear. Rejected: "when they appear" is a second look at
   the disk on every `update`, the kind of guess ADR-0020 rejected, and `layout = "hexagonal"`
   would be stored while nothing enforces it.
2. **Write the missing modules.** Rejected: ADR-0013 writes nothing inside the package.
3. **Refuse, and name them (chosen).** One rule, no new state, nothing half-configured.

For a project adopted before `own_ci` and `own_infra` existed (C9):
1. **Keep looking at the disk as before.** Rejected: it is the finding, and `update` would
   then record the mistake for good.
2. **Decide from the names of the files (chosen)**: only a file RUMBO does not write proves
   the project had its own.

## Decision and rationale
**Backups (C1).** `--force` skips a file whose bytes already equal what it would write (no
backup, listed as unchanged). Otherwise it copies the file to the first free name among `.bak`,
`.bak.1`, `.bak.2`... and makes no copy when one of those already holds the same bytes. A
backup is never overwritten. A symbolic link is never followed nor replaced. `rumbo doctor`
no longer sends anyone to `init --force`: a missing `uv.lock` is fixed by the `uv add` lines
`init` printed, or by `uv lock`.

**Pytest (C2).** On the first adoption RUMBO looks for a pytest configuration, in pytest's own
order: `pytest.toml`, `.pytest.toml`, `pytest.ini`, `.pytest.ini`, `[tool.pytest]` in
`pyproject.toml`, `[pytest]` in `tox.ini`, `[tool:pytest]` in `setup.cfg`. With one, it writes
no `[tool.pytest.ini_options]` and says where the project's is. With none, it writes
`testpaths` and nothing else (no `addopts`): the detected tests directory, followed by every
other directory where test files (`test_*.py`, `*_test.py`) were found; hidden directories,
virtual environments, build output and `spikes/` are not searched. Test files in the project
root itself mean no `testpaths` at all, so pytest keeps collecting as it did. The report says
when no tests directory existed (RUMBO creates `tests/` for its two files) and when tests live
outside the tests directory: pytest collects them, but the sensor, `rumbo trace` and G4 watch
the one directory `[tool.rumbo].tests` names. That directory stays a single top-level folder:
the architecture test locates the project root from its own depth.

**What was already there is not judged on day one, nor changed.** Two things an adopted
project met on its first day, found by the internal audit of this slice:
- The `security` step scanned the whole package, so a stock Django project was red at once
  (bandit reports the framework's sample secret key). Like `lint`, `format` and `types`
  (ADR-0013), the `security` step of an adopted project names `{changed}`: the files a change
  touches. `--full`, which the nightly runs, makes it the whole tree. As in a new project,
  bandit judges the code only: `[tool.bandit]` keeps the environment, the tests directory,
  `spikes/` and `scripts/` (which has its own step) out, also when one of their files is named
  on the command line; otherwise the tests the harness itself adds, which start processes,
  made the first check red. The exclusions are globs: measured with bandit 1.9.4, a plain
  name such as `tests` is matched anywhere in a path and would silently skip
  `pkg/contests.py`.
- The runtime dependencies of a kind (`fastapi`, `uvicorn`, `httpx` for a service; `pydantic`
  and the SDK for an LLM product) exist for the skeleton RUMBO writes. An adopted project gets
  no skeleton, so it gets none of them: a Flask or Django service was being handed FastAPI.
  The development tools of the harness are still added.

**Python (C3).** `rumbo init`, adopting or not, reads `[project].requires-python` and
`.python-version` when the directory has them. Without `--python` the harness uses the lowest
supported Python that `requires-python` allows (clauses `>=`, `>`, `<=`, `<`, `==`, `!=`,
`~=`, with `.*`; a minor series counts when some patch of it satisfies the clause, so `>3.11`
allows 3.11); else the version `.python-version` pins, or the nearest supported one when the
pin is outside the list; else 3.11. `--python` wins when `requires-python` allows it and is
refused when it does not. When `requires-python` allows no supported Python, the command
refuses. A lower bound older than the supported list, a specifier this cannot read and a pin
that is below the result or outside `requires-python` are reported; neither file is rewritten.

**`promote` and `update` (C4, C5).** `promote` builds the configuration of the new level
before it writes anything, and puts `pyproject.toml` back byte for byte when the update that
follows fails. A `[tool.rumbo]` no configuration accepts is one line and exit code 2 in
`update`, `update --diff`, `promote` and `doctor`. `update` compares the release segments of
`[tool.rumbo].version` with its own (numbers only, trailing zeros ignored) and refuses a newer
harness, naming both versions, unless `--allow-downgrade` is given; `promote` refuses too.

**The guard wiring (C6).** A `.claude/settings.json` or `.pre-commit-config.yaml` that exists
is still left untouched. When it does not call the guard, the report prints the exact text to
add: the `hooks` object of the template, and the two local hooks with the two top-level keys
they need. `rumbo doctor` checks it: a problem (exit 1) when settings.json lacks a
`PreToolUse`, `PostToolUse` or `Stop` hook that runs `scripts/rumbo_guard.py`, or the
pre-commit configuration does not run it for `pre-commit` and `commit-msg`; a warning when a
hook is there but its matcher misses a tool the guard judges (`EDIT_TOOLS` and `SHELL_TOOLS`
of `guard.py`). The warning is how a project created before `PowerShell` was matched learns of
it: `update` never rewrites `.claude/settings.json`. `pre-commit autoupdate` runs only on a
configuration this run wrote.

**Only what is on disk (C7).** The package of an adopted project is a directory that exists,
under `src/` or at the root, and keeps the name the disk gives it (`MyPkg`, whatever
`[project].name` says). A project without one (a single module) is refused with the layout
that is supported. A configuration that names modules that are not there is refused before
anything is written, listing them: one directory per layer of a hexagonal or layered layout
(`--llm` forces hexagonal), `<package>/app/entrypoint.py` with `--llm`, `<package>/pipeline.py`
with `--kind data`. A layout that is detected is held to the same rule: `domain/` and `app/`
without `api/` and `adapters/` is refused with `--layout flat` as the way out. A
`pyproject.toml` without `[build-system]` gets no build backend from RUMBO; the report says
the package is not installed and shows one that fits. So what adoption accepts is flat or
already layered, and its checks table names nothing that is missing.

**Names (C8).** `domain`, `app` and `api` are refused only for a new project whose kind and
layout write a sub-package of that name (`app.app`). An adopted project keeps its own name:
any identifier that is not a keyword; only a package at the root named like a directory the
harness writes into (`scripts`, `tests`...) is still refused.

**Decided once (C9).** Adoption records `own_ci` and `own_infra` in `[tool.rumbo]`: whether
the project had a workflow under `.github/workflows/` and an `infra/` directory before RUMBO
wrote anything. Every later command reads the keys. A project adopted before they existed is
judged by names until `rumbo update` writes them: `own_ci` when a workflow is not named
`ci.yml`, `nightly.yml` or `release.yml`, or when there are workflows and no `ci.yml`;
`own_infra` when `infra/` exists without the `Dockerfile` RUMBO writes. The one case this
gets wrong is a project whose own workflow was already called `ci.yml`: `update` lists it as
different from the template and changes nothing.

**Before the first write (C11).** `init` reads, merges and validates everything it has to read
before it writes: the target is a directory, `pyproject.toml` and `.gitignore` are UTF-8 (a
byte order mark is accepted), the merged TOML parses, no file sits where a directory is needed.
An error names the file and leaves the directory as it was. An existing `[tool.rumbo]` without
`package` is refused: the table would be kept and no command could load it.

**The rest (C10, C11).** The architecture test is a harness file under the project's tests
directory. `[tool.rumbo].version` is rewritten on the line after which the file parses to the
same document with only that key changed, and a spelling that cannot be rewritten is reported.
Every file a command writes ends its lines with LF. `rumbo decision` refuses an empty title and
a line break in the title, `--why` or `--who`. `rumbo new` numbers after four-digit prefixes
only and stops at 9999. Inside a repository but below its top, `init` installs no git hook and
says they belong to the root. `update` and `promote` list each check step whose command
differs from the template of the level and each Makefile alias the template has and the
project lacks, and rewrite neither (ADR-0011: the table and the Makefile are the human's).

**What this refines.**
- ADR-0013, "tests directory: `tests` if it exists, else `test` if it exists, else `tests`":
  the fallback is now said in the report, and tests found elsewhere are listed.
- ADR-0013, "Everything else follows the init rules (existing files skipped and reported,
  `pyproject.toml` and `.gitignore` merged)": the merge no longer adds a pytest table over the
  project's own configuration, and never `addopts`.
- ADR-0013, "When `.github/workflows/` already holds a workflow, `ci.yml` is not written" and
  "`infra/` is written only when the kind has it and the directory does not exist": true at
  adoption, and from then on read from `own_ci` and `own_infra`.
- ADR-0013, "layout: `hexagonal` when `src/<pkg>/domain` and `src/<pkg>/app` both exist": the
  detection is unchanged; the result is refused when the other two layers are missing.
- ADR-0013, "Detection is heuristic; the flags remain the authority": a flag that names what
  is not on disk (`--package`, `--llm`, `--kind data`, `--layout`) is refused.
- ADR-0020, "`--adopt` writes `"."` when the package was found at the root": the package must
  be found, and `package` is its name on disk.
- ADR-0020, "`rumbo update` writes the key like the other late keys": `own_ci` and `own_infra`
  join them for adopted projects.
- ADR-0011, "steps are only added, never replaced or removed": still true; the steps that
  differ from the template of the level are now listed.
- ADR-0014, "`rumbo init --python X.Y` (default `3.11`": the default is what the project
  already requires, when it says; `3.11` when it does not.

## Consequences (+/−)
+ A second `--force`, a failed `promote` and an error in the middle of `init` lose nothing.
+ An adopted project keeps its pytest configuration, its Python, its package name, its CI.
+ A guard that is not wired, or wired without `PowerShell`, is visible in `rumbo doctor`.
− `rumbo doctor` exits 1 on a project whose own settings.json was never given the hooks. It
  was unprotected before; now it is told.
− A project with `domain/` and `app/` but no `api/` and `adapters/`, or adopted with `--llm`
  before its entry point exists, is refused where it used to be given a broken configuration.
  The message names the directories and the flag.
− When the modules exist, the example smoke dataset still runs against the project's own
  entry: existence is checked, behaviour is not. The human replaces the two example cases.
− Tests inside the package are collected but not watched by the sensor until they move.
− Two more keys in `[tool.rumbo]` of an adopted project; one more flag (`--allow-downgrade`).

## Reversibility: high
Every rule is a check before a write or a line in a report. `own_ci` and `own_infra` are two
keys that a project may delete: the names decide again and `rumbo update` writes them back.
