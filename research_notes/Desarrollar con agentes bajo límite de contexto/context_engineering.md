# Context engineering for LLM coding agents (2024–2026): techniques, implementations, thresholds, evidence

Research date: 2026-11-01. Scope: how practitioners and vendors keep a single coding agent effective as its context window fills. Primary sources were preferred; several hosts (manus.im, dbreunig.com, martinfowler.com, openai.com, cursor.com, docs.cursor.com, aider.chat, openhands.dev/docs.all-hands.dev, ghuntley.com, simonwillison.net, research.trychroma.com) were unreachable from this session's network, so those items rely on secondary coverage or paper text and are flagged as such.

## Key question 1: What do Anthropic's "Effective context engineering for AI agents" and "Building agents with the Claude Agent SDK" recommend, and with what numbers?

### Takeaway
Anthropic (both posts dated 29 Sep 2025) frames context as a finite "attention budget" subject to "context rot" (a gradient, not a cliff) and recommends four mechanisms for long-horizon work: compaction (summarize then restart), structured note-taking into files outside the window, sub-agents with clean contexts that return 1–2k-token summaries, and just-in-time retrieval via lightweight identifiers (paths, grep/glob) instead of pre-loading. The posts give few hard numbers; the measured figures come from the same-day "context management" API announcement (39% / 29% / 84%) and the June 2025 multi-agent research post (90.2%, 15x tokens).

### Cited Findings
- Published 29 Sep 2025; defines context rot: "as the number of tokens in the context window increases, the model's ability to accurately recall information from that context decreases", described as "a performance gradient rather than a hard cliff"; attention budget framing with n² pairwise relationships for n tokens; "do the simplest thing that works" — [Anthropic, Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Compaction: "summarize a conversation nearing the context window limit and reinitiate a new context window with the summary"; in Claude Code compaction keeps "architectural decisions, unresolved bugs, and implementation details", discards redundant tool outputs, and the agent continues "with the compressed context plus the five most recently accessed files"; tune compaction prompts by first maximizing recall, then precision; tool-result clearing is "one of the safest lightest touch forms of compaction" — [Anthropic, Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Structured note-taking / agentic memory: agent writes notes (e.g. NOTES.md, to-do list) to persistent memory outside the window and pulls them back later; Claude Plays Pokémon example tracked progress like "for the last 1,234 steps"; memory tool launched in public beta with Sonnet 4.5 — [Anthropic, Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Sub-agent architectures: specialized sub-agents work in clean context windows, each may use "tens of thousands of tokens or more" but returns "a condensed, distilled summary of its work (often 1,000-2,000 tokens)"; the post claims "a substantial improvement over single-agent systems" on complex research tasks (no figure given in that post) — [Anthropic, Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Just-in-time retrieval: keep lightweight identifiers (file paths, stored queries, links) and load at runtime; Claude Code uses `head`/`tail` on large data; hybrid model: CLAUDE.md dropped in up front plus glob/grep just-in-time; metadata (folder hierarchy, naming, timestamps) are relevance signals; trade-off: runtime exploration is slower than pre-computed retrieval — [Anthropic, Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Tools: keep tool sets minimal and non-overlapping; "bloated tool sets" are a common failure mode; prefer a few canonical examples over edge-case rule lists; system prompts at the "right altitude" — [Anthropic, Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Agent SDK post (29 Sep 2025): compaction "automatically summarizes previous messages when the context limit approaches", built on Claude Code's `/compact`; subagents exist for parallelization and context management, each with "its own isolated context windows", returning only relevant information; file/folder structure is itself context engineering; Claude loads large files via `grep`/`tail`; recommends starting with agentic search and adding semantic search only if speed is needed; no numeric thresholds stated — [Anthropic/Claude blog, Building agents with the Claude Agent SDK](https://claude.com/blog/building-agents-with-the-claude-agent-sdk)
- Context management API announcement (29 Sep 2025): context editing clears stale tool calls/results "when approaching token limits"; memory tool is a client-side, file-based directory persisting across conversations; Sonnet 4.5 has "context awareness" (tracks available tokens throughout a conversation); internal eval on agentic search: memory tool + context editing = 39% improvement over baseline, context editing alone = 29%; in a 100-turn web-search eval, context editing let agents finish workflows that otherwise failed from context exhaustion while cutting token consumption 84% — [Anthropic/Claude blog, Managing context on the Claude Developer Platform](https://claude.com/blog/context-management)
- Multi-agent research system (13 Jun 2025): multi-agent (Opus 4 lead + Sonnet 4 subagents) beat single-agent Opus 4 by 90.2% on an internal research eval; multi-agent systems use ~15x the tokens of chat (single agents ~4x); token usage alone explained ~80% of performance variance on BrowseComp; beyond the 200,000-token window the lead agent saves its plan to memory; agents summarize completed phases and store essentials externally before new tasks; near context limits agents "spawn fresh subagents with clean contexts" and hand off state; subagents store outputs in external systems and pass lightweight references — [Anthropic, How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)

### Inferences
- Anthropic's own measured gains (39%, 29%, 84%, 90.2%) all come from internal, unpublished evals on search/research tasks, not coding benchmarks; they are vendor claims, not independent results.
- The "five most recently accessed files" detail is the only concrete compaction parameter Anthropic's engineering post gives; it matches the Claude Code docs (see KQ2).

### Gaps
- Neither Anthropic engineering post gives thresholds for when compaction should fire or how much summary should be kept.
- No ablation separating note-taking from compaction on coding tasks was found.

## Key question 2: How do Claude Code and other coding agents (Cursor, Codex CLI, Gemini CLI, Aider, OpenHands) implement context management, with what defaults, and what evaluations exist?

### Takeaway
Claude Code's documented machinery is the most detailed: auto-compaction at a model-dependent window (default = full context; ~967K on native-1M models; `/autocompact`, `autoCompactWindow`, `CLAUDE_CODE_AUTO_COMPACT_WINDOW`), a documented "what survives compaction" table (CLAUDE.md, auto memory, plan file re-injected; up to 5 most-recently-modified files re-read; skill bodies capped 5k/25k tokens), `/compact <focus>`, `/clear`, `/context`, tool-result clearing, idle compaction, and a 200-line CLAUDE.md guideline with auto memory's MEMORY.md capped at 200 lines/25KB. OpenHands ships an LLMSummarizingCondenser (SDK default max_size=80 events, keep_first=4; condenses to half when triggered) and the only rigorous published evaluation (JetBrains "Complexity Trap", NeurIPS 2025 workshop) shows plain observation masking matches LLM summarization on SWE-bench Verified at ~50% lower cost than no management. Cursor, Codex and Gemini CLI documentation was not reachable; thresholds for them are secondary and conflicting.

### Cited Findings

Claude Code — compaction and thresholds
- Default auto-compact threshold: "If you don't set an auto-compact window, Claude Code compacts when the conversation reaches the model's context limit", except: cloud sessions compact "as the conversation approaches the model's limit"; Sonnet 4.6/Opus 4.6 without extended context compact at the 200K boundary; models with a native 1M window (Fable, Sonnet 5+, Haiku 5.5, Opus 4.7+) "compact before the window fills, at about 967K tokens by default"; unrecognized model IDs are assumed 200K — [Claude Code docs, Model configuration: Default auto-compact thresholds](https://code.claude.com/docs/en/model-config)
- Setting the window: `/autocompact <value>` (per model, saved in `modelSettings`; `/autocompact auto` restores the tuned default), `autoCompactWindow` settings key, `--autocompact` flag, `CLAUDE_CODE_AUTO_COMPACT_WINDOW` env var (highest precedence); accepted range 100K–1M tokens, capped at the model's window; subagents can have their own window (`autoCompactWindow` frontmatter, v2.1.296+); `CLAUDE_CODE_DISABLE_1M_CONTEXT=1` makes sessions compact at 200K; `DISABLE_COMPACT` disables compaction — [Claude Code docs, Model configuration](https://code.claude.com/docs/en/model-config); [Claude Code docs, Subagents](https://code.claude.com/docs/en/sub-agents)
- What survives compaction: system prompt and output style still apply; project-root CLAUDE.md, unscoped rules, auto memory, and the plan written in plan mode are re-injected from disk; path-scoped rules and nested CLAUDE.md reload on demand (they are summarized away otherwise); "Files Claude read or edited: Claude Code re-reads up to five, most recently modified first", a file over 5,000 tokens comes back as a path reference; invoked skill bodies re-injected "capped at 5,000 tokens per skill and 25,000 tokens total; oldest dropped first"; background commands/subagents keep running; SessionStart hooks with `compact` source run and add output — [Claude Code docs, Explore the context window](https://code.claude.com/docs/en/context-window)
- Manual controls: `/compact focus on the auth bug fix` ("The summary keeps what you choose instead of what the automatic pass guesses is important"); `/rewind` → "Summarize from here"/"Summarize up to here"; `/autocompact 500k` to compact earlier; `/clear` between unrelated tasks; delegate large reads to subagents; `/context` for a live breakdown; summarization request inherits the session's extended-thinking setting (v2.1.198+) — [Claude Code docs, Explore the context window](https://code.claude.com/docs/en/context-window)
- CLAUDE.md compaction instructions: a `# Compact instructions` section in CLAUDE.md customizes what compaction preserves; `/compact Focus on code samples and API usage` — [Claude Code docs, Manage costs](https://code.claude.com/docs/en/costs)
- The "context or auto-compact warning" is "not a usage limit"; the conversation is close to the auto-compact window — [Claude Code docs, Manage costs](https://code.claude.com/docs/en/costs)
- Idle compaction: a long conversation idle on the one-hour cache TTL can be compacted (`idleCompaction` setting, v2.1.290+); best-practices page: "a session past about 200K tokens that sits idle is compacted shortly before the cache expires" — [Claude Code docs, Prompt caching](https://code.claude.com/docs/en/prompt-caching); [Claude Code docs, Best practices](https://code.claude.com/docs/en/best-practices)
- Tool-result clearing: `/usage` counts "expected rebuilds (compaction or tool-result clearing)" as a distinct cache-miss category, confirming Claude Code also clears old tool results from context — [Claude Code docs, Manage costs](https://code.claude.com/docs/en/costs)
- Image eviction: when a request would exceed image/PDF limits, Claude Code removes a batch of the oldest images — [Claude Code docs, Prompt caching](https://code.claude.com/docs/en/prompt-caching)

Claude Code — prompt caching implications
- Request layered as system prompt → project context (CLAUDE.md, auto memory, rules) → conversation, so rarely changing content comes first; compaction "replaces your message history with a summary. By design, this invalidates the conversation layer", while system prompt and project context can stay cached; the summarization call itself reads the warm prefix from cache so a mid-session `/compact` "costs a fraction of what the context size suggests", but after the TTL expires `/compact` reprocesses history uncached ("why `/compact` costs the most when you resume an old session") — [Claude Code docs, Prompt caching](https://code.claude.com/docs/en/prompt-caching)
- `/rewind` is cheaper than compaction because it truncates back to an already-cached prefix; `/recap` appends rather than replaces, keeping the cache; editing CLAUDE.md mid-session does not apply until `/clear`, `/compact` or restart — [Claude Code docs, Prompt caching](https://code.claude.com/docs/en/prompt-caching)
- Cache TTL: one hour for the main conversation on a subscription within plan usage; five minutes on API key/cloud/usage credits; subagents get five minutes by default; cache invalidators include model switch, effort change (on older models), MCP server/tool definition changes, compaction, many images, upgrades — [Claude Code docs, Prompt caching](https://code.claude.com/docs/en/prompt-caching)
- Cost reality: "Claude Code sends your full conversation with every request", so "a one-line question in a session that has been open all day still draws usage for the whole conversation"; enterprise averages ~$13/developer/active day, $150–250/developer/month, 90% of users under $30/day; `/compact` "is itself a large request"; `/clear` "costs nothing" — [Claude Code docs, Manage costs](https://code.claude.com/docs/en/costs)
- Example cache line from docs: "14 requests · 91% of input tokens from cache · 2 misses" — [Claude Code docs, Manage costs](https://code.claude.com/docs/en/costs)

Claude Code — CLAUDE.md and auto memory
- Two memory systems, both loaded at session start: CLAUDE.md (human-written instructions, scopes: enterprise/managed, project `./CLAUDE.md`, user `~/.claude/CLAUDE.md`, local `./CLAUDE.local.md`) and auto memory (Claude-written notes per repository in `~/.claude/projects/<project>/memory/`, with a `MEMORY.md` index); "Claude treats them as context, not enforced configuration" — [Claude Code docs, How Claude remembers your project](https://code.claude.com/docs/en/memory)
- Size guidance: "target under 200 lines per CLAUDE.md file. Longer files consume more context and reduce adherence"; `@path` imports do not reduce context cost (imported files load together, max depth 4); whole CLAUDE.md files up to 4 MiB load; a startup warning appears when a file is over the recommended length or when files add up past a combined limit; path-scoped `.claude/rules/` and nested CLAUDE.md files load on demand and have a smaller per-file limit — [Claude Code docs, Memory](https://code.claude.com/docs/en/memory)
- Auto memory: "The first 200 lines of MEMORY.md, or the first 25KB, whichever comes first, are loaded at the start of every conversation"; Claude Code reminds Claude to shorten the index when near the limit and errors when over it; main-conversation auto memory is not loaded into subagents (except forks); subagents can have their own persistent memory (`memory: user|project|local`, same 200-line/25KB rule) — [Claude Code docs, Memory](https://code.claude.com/docs/en/memory); [Claude Code docs, Subagents](https://code.claude.com/docs/en/sub-agents)
- Load order: CLAUDE.md files from cwd and every parent directory are concatenated root→cwd; subdirectory CLAUDE.md files load when Claude reads/edits a file there; AGENTS.md is read in place of CLAUDE.md when no CLAUDE.md exists (v2.1.277+) — [Claude Code docs, Memory](https://code.claude.com/docs/en/memory)
- Token-reduction advice: move workflow-specific instructions from CLAUDE.md to skills (loaded on demand); MCP tool definitions deferred by default (only names enter context until used); CLI tools (`gh`, `aws`) are "more context-efficient than MCP servers"; hooks can pre-filter output ("Instead of Claude reading a 10,000-line log file ... a hook can grep for ERROR"); `/usage` recommends e.g. "Trim ~/code/api/CLAUDE.md · 49k tokens per request" when a pattern exceeds 10% of usage — [Claude Code docs, Manage costs](https://code.claude.com/docs/en/costs)
- Subagents: each "runs in its own context window"; "Running tests, fetching documentation, or processing log files can consume significant context. By delegating these to a subagent, the verbose output stays in the subagent's context while only the relevant summary returns"; caveat: "Running many subagents that each return detailed results can consume significant context"; a fresh subagent "first has to gather context your conversation already had, so it can end up slower"; default max spawn depth 3, max 20 concurrent; combined description warning at 15,000 tokens — [Claude Code docs, Subagents](https://code.claude.com/docs/en/sub-agents); [Claude Code docs, Best practices](https://code.claude.com/docs/en/best-practices)
- Agent teams use "approximately 7x more tokens than standard sessions when teammates run in plan mode" — [Claude Code docs, Manage costs](https://code.claude.com/docs/en/costs)
- Notable shift in official advice (best-practices page, current as of Nov 2026): under "What you can stop doing", "The context window is your main constraint, manage it aggressively" is listed as outdated ("Most current models have a 1M-token window and compaction happens on its own, so running out is rare. `/clear` between tasks is still worth doing, because a focused context gets you better answers and costs less"), as is "Use subagents to protect your context window" ("Running out of context is rarely the problem anymore"); still recommended: write a `SPEC.md` then "start a fresh session to build from it, so the build begins with a clean context"; after two failed corrections "run `/clear` and write a better prompt instead of a third" — [Claude Code docs, Best practices](https://code.claude.com/docs/en/best-practices)

OpenHands
- SDK `LLMSummarizingCondenser` (source, read Nov 2026): class defaults `max_size=240` events, `keep_first=2`, `minimum_progress=0.1`; the standard condenser used by the default agent and sub-agents is created with `_DEFAULT_MAX_SIZE = 80` and `_DEFAULT_KEEP_FIRST = 4`; triggers: explicit request, token count exceeding the stricter of `max_tokens` and the agent LLM's effective input limit (a HARD requirement), or event count > `max_size` (SOFT); on trigger it forgets events so the view shrinks to `max_size // 2` (or to half the token cap), never forgets the leading system prompt or the first `keep_first` events, inserts an LLM-generated summary at the forgetting point, and has a "hard context reset" that summarizes everything with up to 5 retries shrinking event strings by 0.8x — [OpenHands software-agent-sdk, llm_summarizing_condenser.py](https://github.com/OpenHands/software-agent-sdk/blob/main/openhands-sdk/openhands/sdk/context/condenser/llm_summarizing_condenser.py)
- OpenHands SDK docs (search snippet only; host unreachable) describe LLMSummarizingCondenser as the default and claim "up to 2x reduction in per-turn API costs" without stating the benchmark — [OpenHands SDK docs, Context condenser (snippet)](https://docs.openhands.dev/sdk/guides/context-condenser)
- The OpenHands SDK paper (Nov 2025) cites OpenHands' April 2025 blog post on context condensation as the main write-up of the feature; no dedicated OpenHands arXiv paper on condensation was found — [OpenHands Software Agent SDK, arXiv 2511.03690](https://arxiv.org/pdf/2511.03690)

Published evaluation: JetBrains "The Complexity Trap" (NeurIPS 2025 workshop; v1 29 Aug 2025, v3 27 Oct 2025)
- Setup: SWE-agent on SWE-bench Verified (500 instances), 5 model configs (Qwen3-32B thinking/non-thinking, Qwen3-Coder-480B, Gemini 2.5 Flash thinking/non-thinking), turn limit 250; Observation Masking keeps the last M=10 observations and replaces older ones with a placeholder while preserving all reasoning/actions; LLM-Summary uses an adapted OpenHands prompt, summarizing N=21 turns and keeping M=10 tail turns; observation tokens are ~84% of an average SWE-agent turn — [Lindenbauer et al., arXiv 2508.21433](https://arxiv.org/abs/2508.21433)
- Results (solve rate / cost per instance): Qwen3-Coder 480B raw 53.4% / $1.29, masking 54.8% / $0.61 (-52.7%), summary 53.8% / $0.64 (-50.4%); Gemini 2.5 Flash raw 32.8% / $0.41, masking 35.6% / $0.18 (-56.1%), summary 36.0% / $0.24 (-41.5%); Gemini 2.5 Flash (thinking) raw 40.4% / $0.56, masking 36.4% (-9.9%, significant) / $0.24, summary 31.4% (-22.3%, significant) / $0.25; Qwen3-32B raw 17.0% / $1.12, masking 15.0% / $0.55, summary 16.0% / $0.50; Qwen3-32B (thinking) raw 23.0% / $0.51, masking 24.6% / $0.46, summary 24.8% / $0.51 — [Lindenbauer et al., arXiv 2508.21433](https://arxiv.org/abs/2508.21433)
- Conclusions: "any of the discussed management strategies are preferable to none"; both strategies cut cost by >50% on long trajectories; "in three of our five setups, the most efficient strategy also achieved a higher solve rate than the Raw Agent" ("beyond a certain point, more context becomes a liability"); LLM-Summary "does not consistently, or significantly outperform Observation Masking" — [Lindenbauer et al., arXiv 2508.21433](https://arxiv.org/abs/2508.21433)
- "Trajectory elongation effect": LLM-Summary produced longer trajectories (Gemini 2.5 Flash mean 52 turns vs 44 with masking and 50 raw, +15%/+4%; Qwen3-Coder +15% vs raw), suggesting summaries "mask failure signals that would otherwise prompt earlier termination" and "act as a reinforcing signal, encouraging the agent to keep going"; summary-generation API calls cost up to 7.2% of instance cost and defeat prefix caching — [Lindenbauer et al., arXiv 2508.21433](https://arxiv.org/abs/2508.21433)
- Hybrid (masking during accumulation, summary deferred to N=43 as last resort): -7% cost vs masking, -11% vs summary, +2.6 pp solve rate on Verified-50; naive hybrid hyperparameters (N=21) degraded efficiency due to KV-cache inefficiency — [Lindenbauer et al., arXiv 2508.21433](https://arxiv.org/abs/2508.21433)
- OpenHands generality check (v0.43.0, Verified-50, Gemini 2.5 Flash): the masking window must be retuned per scaffold (M=10 "degrades drastically", M=58 works) because OpenHands retains retry turns SWE-agent elides; after tuning, masking matches LLM-Summary on cost and solve rate — [Lindenbauer et al., arXiv 2508.21433](https://arxiv.org/abs/2508.21433)
- Limitations the authors state: SE-only domain with verbose tool outputs favors masking; fixed heuristic triggers (fixed window keeps stale file contents after modification) — [Lindenbauer et al., arXiv 2508.21433](https://arxiv.org/abs/2508.21433)

Learned context management
- "Context as a Tool" (26 Dec 2025; ACL Findings 2026): SWE-Compressor, a model trained to decide when to compress its own context, reports 57.6% on SWE-bench Verified and claims to "significantly outperform" ReAct and static compression baselines under a bounded context budget; no cost/length figures in the abstract — [Liu et al., arXiv 2512.22087](https://arxiv.org/abs/2512.22087)

Gemini CLI (code moved; defaults conflicting)
- Gemini CLI has a `/compress` command and automatic compression; code analyses give the default trigger as 0.5 of the model token limit (`DEFAULT_COMPRESSION_TOKEN_THRESHOLD = 0.5`, so ~524K on a 1,048,576 default), while other articles report 0.7; one analysis says the most recent ~30% of history is preserved and the older 70% compressed; GitHub issue #23906 proposes changing the default — [ryogrid gist](https://gist.github.com/ryogrid/16d5abef3df92c969d2ef3a598973b03); [lin-guanguo research](https://lin-guanguo.github.io/llm-memory-research/gemini-cli.research/); [gemini-cli issue #23906](https://github.com/google-gemini/gemini-cli/issues/23906)

Aider (docs unreachable; repo copy read)
- Repo map: a graph with source files as nodes and dependency edges, ranked by a graph ranking algorithm; aider sends the highest-ranked symbols/signatures that fit the `--map-tokens` budget, "defaults to 1k tokens", resizes dynamically, and can expand "well beyond the budget when no files have been added to the chat"; purpose is to give the LLM whole-repo awareness without loading files — [Aider repo, docs/repomap.md](https://raw.githubusercontent.com/Aider-AI/aider/main/aider/website/docs/repomap.md)

### Inferences
- Across vendors the mechanisms converge: (a) threshold-triggered summarization near the window limit, (b) retention of a recent tail, (c) re-injection of durable files (CLAUDE.md/AGENTS.md, plan/spec, memory) after compaction, (d) offloading verbose output to subagents or files. Only Claude Code documents exactly what the summary retains.
- The Complexity Trap is the only rigorous head-to-head measurement found; it suggests cheap truncation of old tool outputs captures most of the benefit, and that LLM summaries can harm by hiding "give up" signals. This is consistent with Anthropic calling tool-result clearing the "safest, lightest-touch" form of compaction.
- Claude Code's official stance has shifted (2025 → late 2026) from "manage context aggressively" to "running out is rare; clear between tasks for quality and cost", driven by 1M windows and auto-compaction.

### Gaps
- No public, controlled evaluation of Claude Code's or Cursor's compaction quality (task success before vs after compaction) was found.
- OpenHands' April 2025 condenser blog (with its SWE-bench with/without-condenser numbers) could not be fetched; only the SDK code and the "up to 2x" docs snippet were available.
- Current Gemini CLI compression threshold could not be confirmed from source (the service file has moved); 0.5 vs 0.7 remains unresolved.
- Codex CLI per-model auto-compact defaults and the 90% clamp are unverified.

## Key question 3: Memory/handoff documents (plan files, progress.md, handoff notes, scratchpads) and the Manus "context engineering" lessons: patterns and evidence

### Takeaway
File-based externalization is the common pattern: Claude Code re-injects the plan-mode plan and MEMORY.md after compaction and recommends a written SPEC.md as a handoff into a fresh session; Anthropic's research agent saves its plan to memory past 200K tokens; Manus (Jul 2025) formalized "file system as context", todo.md "recitation", "mask don't remove" tools, "keep the wrong stuff in", and KV-cache hit rate as the top production metric. Evidence is mostly practitioner report; the one quantitative hint is an academic finding that having the model "recite" relevant evidence before solving recovers some long-context loss (up to 4% on RULER).

### Cited Findings
- Manus "Context Engineering for AI Agents: Lessons from Building Manus" (Yichao 'Peak' Ji, 18 Jul 2025): six lessons — design around the KV-cache (stable prompt prefix, append-only context, deterministic serialization); "mask, don't remove" tools (logit masking rather than dynamic tool removal, because tool definitions near the front invalidate the cache); use the file system as unlimited, restorable context (keep paths/URLs, drop content); "manipulate attention through recitation" by rewriting a `todo.md` at the end of context each step; "keep the wrong stuff in" (error traces enable adaptation; error recovery is "one of the clearest indicators of true agentic behavior"); avoid few-shot uniformity ("The more uniform your context, the more brittle your agent becomes") — [cedrickchee gist summarizing the Manus post](https://gist.github.com/cedrickchee/b9646b3007b4a15f528351abd331984f); original at [Manus blog](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus) (unreachable from this session)
- Manus numbers as reported by secondary sources (not verified against the original): average input:output token ratio ≈100:1; cached input ≈$0.30/MTok vs $3/MTok uncached for Claude Sonnet (10x); KV-cache hit rate is "the single most important metric" for a production agent — [besthub summary](https://www.besthub.dev/articles/mastering-context-engineering-for-ai-agents-kv-cache-tool-management-and-error-handling-b3ec0cea51e1); [panqiwei wiki summary](https://panqiwei.github.io/advanced-agentic-dev-patterns/en/wiki/sources/manus-context-engineering)
- Secondary coverage also reports a later Manus evolution: the executor's direct todo.md maintenance consumed roughly one-third of all actions, so Manus moved planning to a dedicated planner sub-agent; this detail could not be verified in the original post — [tianpan.co summary (search snippet)](https://tianpan.co/blog/2026/03/02/context-engineering-lessons-from-manus)
- Claude Code: the plan written in plan mode is "re-injected from disk" after compaction; auto memory `MEMORY.md` (index) plus topic files persist across sessions and are re-injected after compaction; `SPEC.md` workflow: interview → write spec → "start a fresh session to build from it, so the build begins with a clean context and a written definition of done" — [Claude Code docs, Context window](https://code.claude.com/docs/en/context-window); [Claude Code docs, Best practices](https://code.claude.com/docs/en/best-practices)
- Anthropic research agent: lead agent "saves its plan to Memory" because context beyond 200,000 tokens is truncated; agents "summarize completed work phases and store essential information in external memory before proceeding"; subagents write outputs to a filesystem and pass "lightweight references" — [Anthropic, multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)
- Anthropic's memory tool (Sep 2025) is a client-side file directory (create/read/update/delete) persisting across conversations; combined with context editing it gave +39% on internal agentic-search evals — [Claude blog, context management](https://claude.com/blog/context-management)
- Cursor saves chat history to a file before summarizing and hands the agent a reference to it, so lost details remain recoverable (secondary snippet) — [Cursor blog, Dynamic context discovery (snippet)](https://cursor.com/en-US/blog/dynamic-context-discovery)
- Recitation evidence (academic, not agent-specific): "Context Length Alone Hurts LLM Performance Despite Perfect Retrieval" (EMNLP 2025 Findings, Oct 2025): across 5 LLMs performance drops 13.9%–85% as input length grows even with perfect retrieval and even when irrelevant tokens are whitespace or masked; prompting the model to recite the retrieved evidence before solving improves GPT-4o on RULER by up to 4% — [Du et al., arXiv 2510.05381](https://arxiv.org/abs/2510.05381)
- Ralph-loop variants keep "state in files and git" as the only memory across iterations (see KQ4) — [ralph-orchestrator docs](https://mikeyobrien.github.io/ralph-orchestrator/concepts/ralph-wiggum-technique)

### Inferences
- The Manus recitation technique and the Du et al. recitation result point the same way: re-stating goals/evidence at the recency end of the context mitigates attention decay. The Manus one-third-of-actions overhead (if accurate) shows recitation has a real cost that pushed them toward a separate planner.
- Plan/spec/memory files are what make compaction and fresh sessions safe: Claude Code explicitly re-injects them, which is why the official advice treats SPEC.md + fresh session as the handoff mechanism.

### Gaps
- No controlled study measuring task success with vs without a handoff/progress file for coding agents was found.
- The Manus post's exact figures (100:1, $0.30 vs $3, ~50 tool calls/task) could not be verified from the primary text (host blocked).

## Key question 4: Task decomposition for context — "one task per session", fresh-context loops (Ralph Wiggum), OpenAI harness engineering, Böckeler

### Takeaway
"Fresh context per task" is now mainstream advice: Claude Code's docs say `/clear` between unrelated tasks and start the build in a fresh session from a spec; OpenAI's harness-engineering write-up (Feb 2026, secondary) treats context as scarce, keeps AGENTS.md to ~100 lines as a map into a `docs/` directory that is the system of record, and automates doc gardening; the Ralph Wiggum loop (Huntley, mid-2025) restarts the agent process each iteration with files/git as memory, while Anthropic's official plugin keeps one session (Stop hook) and accumulates context, which critics say "isn't Ralph". No benchmark compares fresh-context loops with single long sessions.

### Cited Findings
- Claude Code official guidance: "`/clear` between unrelated tasks. It costs nothing, and it means the next task doesn't keep paying for the previous one's history"; "If you've corrected the same thing twice and it's still wrong ... `/clear` plus one new prompt that folds in what you learned works better almost every time"; "a focused context gets you better answers and costs less"; a second session is "the easiest independent reviewer" because it hasn't watched the code being written; `/code-review` reviews in "a fresh subagent that never saw your conversation. It isn't swayed by the reasoning that produced the code" — [Claude Code docs, Best practices](https://code.claude.com/docs/en/best-practices)
- Claude Code costs page: "Clear between tasks ... Stale context wastes tokens on every subsequent message"; unexpectedly high spend "usually traces back to long sessions that were never cleared" — [Claude Code docs, Manage costs](https://code.claude.com/docs/en/costs)
- OpenAI "Harness engineering: leveraging Codex in an agent-first world" (secondary; primary unreachable): a small team produced ~1M lines of code with "zero manually-written code in five months"; "context is a scarce resource", a giant instruction file "crowds out the task, the code, and the relevant docs"; they abandoned "one big AGENTS.md" for a ~100-line AGENTS.md acting as a map with pointers to a structured `docs/` directory treated as the system of record (plans, tech debt, design docs versioned in the repo); a recurring "doc-gardening" agent opens PRs to fix stale docs; linters/CI enforce doc structure and layering; Codex loads AGENTS.md root→cwd with a 32 KiB combined cap; dates reported variously as 11 Feb 2026 or Mar 2026 — [search summary A](https://ai-playbooks.pages.dev/reviews/harness-engineering-leveraging-codex-in-an-agent-first-world); [search summary B](https://gu-log.vercel.app/en/posts/en-sp-98-20260303-openai-harness-engineering); [search summary C](https://www.louisbouchard.ai/harness-engineering/)
- Böckeler (Thoughtworks, martinfowler.com "Context Engineering for Coding Agents"; primary unreachable): secondary descriptions say the piece maps the context-configuration landscape using Claude Code as the case study (CLAUDE.md files, progressive skill disclosure, sub-agent isolation); her QCon London 2026 keynote reports agents "can now run unsupervised for up to 20 minutes" — [InfoQ, state of AI coding](https://infoq.com/news/2026/03/ai-coding-state); [developertoolkit glossary citing the article](https://developertoolkit.ai/en/glossary/context-engineering/)
- Ralph Wiggum loop: popularized July 2025 by Geoffrey Huntley ("Ralph is a Bash loop"); a shell loop pipes the same prompt into headless `claude` each pass, so "each Claude Code invocation gets a fresh context window" and "the only memory is the filesystem and git history"; proponents argue errors in one iteration don't bleed into the next — [Steve Kinney, The Ralph Loop](https://stevekinney.com/writing/the-ralph-loop); [ralph-orchestrator docs](https://mikeyobrien.github.io/ralph-orchestrator/concepts/ralph-wiggum-technique); [shipyard.build on Ralph loops](https://shipyard.build/blog/claude-code-ralph-loop/)
- Critique: Anthropic's official `ralph-wiggum` plugin uses a Stop hook that keeps one session, so "context accumulates instead of resetting" and relies on compaction; critics call it "safer but less effective"; a January 2026 practitioner post is titled "I mostly stopped using Ralph"; Reddit users warn token usage is high ("probably not for the $20/month Pro plan"); some loop tools blur the line by compacting at "redline thresholds" and only then instantiating a fresh context — [second-brain post on the plugin](https://second-brain-nuxt.vercel.app/ralph-wiggum-and-why-claude-codes-implementation-isnt-it); [Tom Wojcik, Jan 2026](https://tomwojcik-com.pages.dev/posts/2026-01-15/ralph-claude-code); [Reddit snapshot](https://reddit.sentinel-team.org/posts/1qlqaub/snapshots/2026-01-24T19%3A24%3A54.066037Z)
- Anthropic's own plugins now live in the `claude-plugins-official` repo; the `anthropics/claude-code` plugins directory no longer holds the plugin README — [anthropics/claude-code plugins/README.md](https://github.com/anthropics/claude-code/blob/main/plugins/README.md)
- Anthropic research system: effort scaling rules (simple fact-finding: 1 agent, 3–10 tool calls; comparisons: 2–4 subagents with 10–15 calls each; complex research: 10+ subagents) and checkpoint/resume instead of restart — [Anthropic, multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)

### Inferences
- The decomposition advice rests on two mechanisms with evidence: (1) smaller contexts perform better (context rot, Du et al.), and (2) a fresh reviewer is not anchored by prior reasoning (Claude Code docs). The fresh-context loop additionally prevents "context poisoning" from compounding, but at the price of re-gathering context each iteration (Claude Code docs note subagents can be slower for this reason).
- OpenAI's and Anthropic's guidance converge on short top-level instruction files (~100 lines / under 200 lines) plus progressive disclosure (docs/ directory, skills, path-scoped rules).

### Gaps
- No measured comparison of Ralph-style fresh-context loops vs single-session compaction on any benchmark was found; all claims are anecdotal.
- OpenAI's harness post and Böckeler's article could not be read in primary form; figures (1M LOC, ~100 lines, 32 KiB) are from secondary sources.

## Key question 5: Measured effects — does compaction/summarization help or hurt; failure taxonomies; trajectory length vs success

### Takeaway
The measured picture: context management is a cost necessity (>50% savings) and roughly neutral-to-slightly-positive for SWE-bench success, with the caveat that LLM summaries can lengthen trajectories and, for one thinking model, cut solve rate 22%; long contexts degrade models even with perfect retrieval (13.9–85%); Breunig's June 2025 taxonomy (poisoning, distraction, confusion, clash) is the standard vocabulary; and the "longer trajectories = failure" finding (failed runs 12.6–82.5% longer) reverses once task difficulty is controlled (resolved runs 10% longer within-task), so length is an ambiguous signal while read-before-edit and validation effort are robust predictors.

### Cited Findings
- Compaction effects on SWE-bench Verified (SWE-agent): both masking and summarization cut cost >50% on long trajectories; solve-rate deltas vs raw ranged from -22.3 pp (LLM-Summary, Gemini 2.5 Flash thinking, significant) to +9.8% (LLM-Summary, Gemini 2.5 Flash non-thinking, not significant); 3 of 5 configs saw the cheapest strategy also score higher than raw — [Lindenbauer et al., arXiv 2508.21433](https://arxiv.org/abs/2508.21433)
- Summarization side effect: LLM-Summary lengthened mean trajectories by 13–15% vs masking/raw, with summaries acting "as a reinforcing signal, encouraging the agent to keep going", and summary calls cost up to 7.2% of instance cost while breaking cache reuse — [Lindenbauer et al., arXiv 2508.21433](https://arxiv.org/abs/2508.21433)
- Context length alone hurts: 13.9%–85% performance drop across 5 LLMs on math/QA/coding as input grows, within claimed context limits, persisting when irrelevant tokens are whitespace or fully masked; recitation mitigates (up to +4% GPT-4o on RULER) — [Du et al., arXiv 2510.05381](https://arxiv.org/abs/2510.05381)
- Chroma "Context Rot" technical report (14 Jul 2025; primary unreachable): tested 18 models (GPT-4.1, Claude 4, Gemini 2.5, Qwen3 among them); performance grows "increasingly unreliable as input length grows"; needle-in-a-haystack scores don't predict real long-context performance; all 18 models did better on shuffled haystacks than logically structured ones; caveat that Chroma is a vector-DB vendor — [secondary summary](https://devthinkai.github.io/devthink-archive/articles/2025-07-28_context-rot-how-llms-degrade-with-longer-context-windows-057d); [paper review](https://rosetta.to/u/mattpalmer/context-rot-takeaways-from-the-latest-chroma-research-paper-review)
- Breunig taxonomy ("How Long Contexts Fail", 22 Jun 2025; primary unreachable): context poisoning (a hallucination enters context and is repeatedly referenced, e.g. Gemini 2.5 Pokémon agent pursuing impossible goals), context distraction (model over-focuses on accumulated context and repeats past actions instead of reasoning; Gemini agent reportedly degraded past ~100,000 tokens), context confusion (superfluous content/tools degrade responses; a Berkeley Function-Calling example of an 8B model handling 19 tools but failing at 46), context clash (correct but contradictory information); fixes: RAG, tool loadout, context quarantine (sub-agents/threads), pruning, summarization, offloading — [Breunig, dbreunig.com (original URL)](https://www.dbreunig.com/2025/06/22/how-contexts-fail-and-how-to-fix-them.html); [CS146S handbook summary](https://fireman333.github.io/CS146S-handbook-zh/readings/w3_how_long_contexts_fail/); [Simon Willison, 29 Jun 2025 (snippet)](https://simonwillison.net/2025/Jun/29/)
- Trajectory length vs success (Majgaonkar et al., ICSE 2026 preprint, 31 Oct 2025): across OpenHands, SWE-agent, Prometheus on SWE-bench Lite/Verified, "failed trajectories are longer and have a wider distribution than successful ones"; failed runs 12.6% (Lite) / 18.5% (Verified) longer for SWE-agent, 31.0% / 82.5% for OpenHands, 56.6% / 50.7% for Prometheus (e.g. OpenHands Verified mean 54.05 steps success vs 98.62 failure); authors suggest "early stopping or trajectory monitoring could reduce wasted computation"; failures that locate the right file (72–81%) still fail at finer-grained reasoning; agents "need mechanisms to abandon unproductive reasoning loops" — [Majgaonkar et al., arXiv 2511.00197](https://arxiv.org/abs/2511.00197)
- Confound reversal (Mehtiyev & Assunção, 2 Apr 2026): 9,374 trajectories, 19 agents (8 frameworks, 14 LLMs), 500 SWE-bench Verified tasks; fixing the agent, failures are 14.0%–111.9% longer (all p<0.001), but trajectory length rises with task difficulty for every agent; fixing the task, resolved trajectories are longer on 63% of 416 contested tasks (44.0 vs 39.6 steps, +10%, p=1.9e-9); "trajectory length should not be used as a standalone signal for failure detection"; robust predictors: delaying the first edit (ρ=+0.68), lower opening patch intensity (ρ=-0.78), validation share (ρ=+0.50; strong agents validate 35–37% of steps vs 12–19%); these strategies are agent-determined and flat across task complexity; 12.4% of total compute is spent on the 55 never-solved tasks; LLM identity dominates framework (same-LLM agents agree on 85–93% of tasks) — [Mehtiyev & Assunção, arXiv 2604.02547](https://arxiv.org/abs/2604.02547)
- Anthropic (vendor, internal): context editing +29%, +memory +39%, 84% fewer tokens on a 100-turn search eval; multi-agent +90.2% at ~15x tokens — [Claude blog, context management](https://claude.com/blog/context-management); [Anthropic, multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)

### Inferences
- The empirical evidence supports "manage context, but prefer the cheapest mechanism that works": truncating old tool outputs is as effective as LLM summaries on SWE-bench and avoids trajectory elongation; summaries are better reserved as a last resort for very long runs (the paper's hybrid).
- Breunig's four failure modes map onto the vendor mechanisms: poisoning → fresh sessions/`/clear`; distraction → compaction and recitation; confusion → deferred tool loading and small CLAUDE.md; clash → spec/plan files as a single source of truth.
- Trajectory length is a poor stop signal; "read-before-edit" and validation share are better monitors, which supports instructions that force context gathering before edits.

### Gaps
- No study was found that measures task success immediately before vs after a compaction event within one session (the direct "does compaction hurt" question) for Claude Code, Cursor or Codex.
- Breunig's original numbers (e.g. the 100k-token distraction ceiling; Databricks ~32k figure; 39% drop in sharded-prompt study) could not be verified from the primary post in this session.
- Chroma's exact degradation figures were not verifiable (primary unreachable).
